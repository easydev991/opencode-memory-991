# Spec Delta

## Purpose

Хранилище памяти на диске: где лежат памяти, в каком формате, как гарантируется целостность записей и что происходит при сбоях. Владеет всем, что касается состояния на диске.

## ADDED Requirements

### Requirement: Расположение хранилища

Система SHALL размещать памяти проекта в каталоге `~/.local/share/opencode-memory/projects/<slug>-<hash16>/memory/`, где `<hash16>` — первые 16 hex-символов SHA-256 канонического идентификатора проекта, `<slug>` — sanitised basename проекта. Канонический идентификатор проекта — поле `canonical` объекта проекта из контекста opencode (`location.project.canonical`: канонический путь проекта/воркспейса). Переменная `XDG_DATA_HOME` MUST перенаправлять корень `~/.local/share`.

#### Scenario: Переменная XDG перенаправляет корень

- **WHEN** `XDG_DATA_HOME=/tmp/xdg` задана в окружении процесса плагина
- **THEN** памяти проекта создаются в `/tmp/xdg/opencode-memory/projects/<slug>-<hash16>/memory/`

#### Scenario: Разные проекты изолированы

- **WHEN** два проекта имеют разные канонические идентификаторы
- **THEN** их памяти лежат в разных каталогах и не смешиваются

### Requirement: Формат файлов и индекса

Каждая память MUST храниться плоским файлом `<name>.md` с YAML-frontmatter `name`, `description` и `metadata.type` со значением `user|feedback|project|reference`; связи между памятями MUST выражаться вхождениями `[[name]]` в теле. Индекс `MEMORY.md` MUST содержать одну строку на память формата `- [Title](file.md) — hook`, где `Title` — frontmatter-поле `name`, `file.md` — `<name>.md`, а `hook` — frontmatter-поле `description`, сведённое к одной строке (переносы строк схлопываются в пробелы).

#### Scenario: Файл читается без конвертации

- **WHEN** память сохранена
- **THEN** файл открывается любым текстовым редактором, frontmatter и тело осмысленны без дополнительных инструментов

#### Scenario: Индекс соответствует файлам

- **WHEN** в хранилище N файлов памяти (без повреждённых; все N записей помещаются в лимит индекса)
- **THEN** `MEMORY.md` содержит ровно N строк-записей

### Requirement: Атомарная запись под кросс-процессным локом

Запись файла памяти и индекса MUST быть атомарной (временный файл + переименование) и MUST выполняться под кросс-процессным файловым локом с таймаутом. Значение таймаута MUST быть зафиксировано при реализации именованной константой и закреплено тестом; спецификация задаёт только поведение деградации при таймауте (см. «Деградация при таймауте лока»), а не число.

#### Scenario: Параллельные записи двух процессов не теряются

- **WHEN** два процесса opencode одновременно сохраняют разные памяти одного проекта
- **THEN** обе памяти присутствуют на диске и в индексе, файлы не повреждены

### Requirement: Деградация при таймауте лока

Если лок не взят за таймаут, чтение для инжекта SHALL использовать последний закоммиченный файл без записи, а запись SHALL отказывать с structured-ошибкой. `memory_list` при таймауте лока подчиняется тому же правилу fail-open: возвращается последний закоммиченный `MEMORY.md`, а не ошибка. Процесс MUST продолжать работу.

#### Scenario: Лок удерживается сторонним процессом

- **WHEN** другой процесс удерживает лок дольше таймаута
- **THEN** инжект возвращает последнее известное содержимое, `memory_list` возвращает последний закоммиченный индекс, попытка записи возвращает structured-ошибку, сессия не падает

### Requirement: Tolerant чтение повреждённых файлов

Файл с повреждённым frontmatter MUST изолироваться (карантин), а не приводить к падению или молчаливому исчезновению; остальные файлы MUST читаться. Повреждённый файл MUST остаться различимым для пользователя (карантин-каталог или явная пометка).

#### Scenario: Повреждённый файл изолируется

- **WHEN** один `<name>.md` содержит невалидный frontmatter
- **THEN** остальные памяти доступны, повреждённый файл перемещён/помечен, процесс не падает

### Requirement: Редактирование кредов на входе записи

Токены, пароли, API-ключи и другие секреты MUST редактироваться на входе записи и MUST отсутствовать на диске; при сборке индекса из файлов редакция SHALL применяться повторно (защита от ручных правок).

#### Scenario: Секрет не попадает на диск

- **WHEN** `memory_save` получает текст, содержащий API-ключ
- **THEN** на диске сохраняется текст с отредактированным значением, оригинал нигде не записан

### Requirement: Дедупликация содержимого при записи

Сохранение текста, чей канонический ключ совпадает с существующей памятью (NFKC-нормализация, нижний регистр, схлопывание пробелов и пунктуации; ключ `<type>:<canonical>`), SHALL не создавать новый файл: возвращается ответ «already saved» с указанием существующей записи.

#### Scenario: Повторное сохранение идентичного текста

- **WHEN** `memory_save` вызывается второй раз с тем же содержимым (возможно, отличающимся пробелами и регистром)
- **THEN** файл на диске один, ответ идентифицирует существующую память

### Requirement: Лимит размера индекса

Если `MEMORY.md` превышает 200 строк или 25 000 символов, сборка индекса MUST применять бюджетную адмиссию: сначала памяти типов `user` и `feedback`, затем остальные по сортировке до лимита. Усечённый список MUST завершаться финальной строкой-маркером обрезки.

#### Scenario: Индекс не разрастается

- **WHEN** в хранилище больше памятей, чем влезает в лимит, в том числе старая память типа `user` среди множества более новых `project`-памятей
- **THEN** `MEMORY.md` в пределах 200 строк / 25 000 символов, содержит гарантированные `user`/`feedback`, новейшие из остальных записей и маркер обрезки

#### Scenario: Маркер входит в бюджет

- **WHEN** сборка индекса усекает список
- **THEN** итоговый `MEMORY.md` с учётом строки-маркера остаётся в пределах 200 строк / 25 000 символов

### Requirement: Stale-пометка возраста в индексе

При сборке индекса память старше порога по своему типу MUST получать в конце строки индекса пометку возраста формата `[N d old, verify]`; возраст определяется по mtime файла памяти. Пороги: `project` — 60 дней, `user` и `reference` — 90 дней; памяти типа `feedback` MUST не помечаться.

#### Scenario: Старая память помечается возрастом

- **WHEN** в хранилище есть `project`-память старше 60 дней и `feedback`-память любого возраста
- **THEN** строка индекса `project`-памяти содержит пометку возраста, строка `feedback`-памяти — нет

### Requirement: Синхронное обновление индекса

После каждой успешной записи индекс MUST пересобираться синхронно, до возврата ответа инструмента; отложенная (debounce) консистентность индекса MUST не вводиться. Удаление памяти (`memory_delete`) вне скоупа этого change (опциональный будущий этап); при его появлении синхронное обновление индекса распространяется и на удаление.

#### Scenario: Чтение сразу после записи

- **WHEN** `memory_save` вернул успех и следом вызван `memory_list`
- **THEN** список содержит новую память
