# Design

## Context

Текущее состояние: пакет `ocm991@0.1.0` опубликован в npm; server-entrypoint `exports["./server"] → src/plugin.ts` с default-экспортом `{ id, setup }` уже есть; подключение на хосте идёт через легаси-ключ `"plugin"` главного конфига; README описывает устаревшую ручную установку; типы Promise API повторены локально в `src/plugin.ts` без зависимости от официального пакета.

Проверенные факты о хосте v2.2.5, определяющие подход:

- `plugin add` резолвит entrypoints по exports-сабпатам (server → `["server", ""]`); при найденном server/gui entrypoint пакет записывается в канонический массив `"plugins"`, при tui-only — в cli.json.
- Кэш установки: `~/.cache/opencode/npm/<pkg>@<spec>/<ts>`; `spec = "latest"`, если в конфиге литерал совпадает с именем пакета — `ocm991` и `ocm991@latest` дают один каталог, но литерал в конфиге определяет матчинг `update`/`check`.
- Легаси-ключ `"plugin"` ещё читается конфигом, но цели `update`/`check` матчатся дословно против литерала `"plugins"` — поэтому подключение через `"plugin"` не покрывается штатным обновлением.
- Один plugin id под двумя литеральными целями → duplicate failure: держать `ocm991` одновременно в `"plugin"` и `"plugins"` нельзя.
- `plugin list`/`check` из «холодной» директории могут вывести «No plugins found» (инвентарь строится лениво) — верить повторному вызову из той же директории; `--standalone` пуст всегда.
- Официальный пакет типов `@opencode/plugin` (на момент планирования v2.2.3; актуальный latest — v2.2.6, dependencies сверены на 2.2.6) не types-only: его `dependencies` включают `@ai-sdk/provider`, `effect`, `@opencode/ai`, `@opencode/client`, `@opencode/protocol`, `@opencode/schema`, `@opencode/util`. Поверхность Promise API (setup → Cleanup, `session.hook`, `tool.transform`, `event.subscribe`) в нём экспортируется из `./dist/promise`.

## Goals / Non-Goals

**Goals:**

- Пакет распознаётся и подключается штатной командой `opencode plugin add ocm991` на хосте v2.2.5.
- Обновление контролируется командой `opencode plugin update ocm991`.
- Метаданные пакета соответствуют стандарту плагинов v2 (keyword `opencode-plugin`).
- README описывает штатный механизм; главный конфиг пользователя переведён на `"plugins"`.
- Поведение памяти (спеки memory-context / memory-storage / memory-tools) не меняется; тесты зелёные до и после каждой правки.

**Non-Goals:**

- Любые изменения форматов хранения, схемы памяти, инструментов, fail-open, локов, redaction.
- Перевод custom-configs (уже на `"plugins"`).
- Публикация в npm — выполняется только по явному подтверждению пользователя, отдельным шагом.
- Поддержка легаси-ключа в документации и спеках.

## Decisions

1. **Имя пакета — оставить `ocm991`** (решение согласовано с пользователем при планировании). Namespace не влияет на работоспособность: имя — только литерал spec в конфиге, резолв entrypoint идёт по exports, установка/обновление/кэш работают одинаково для scoped и не-scoped имён; переименование было бы breaking-миграцией (новый литерал у установивших, duplicate-риск при переходе). Если namespace понадобится — отдельный change.
2. **Entrypoint не расширять.** Альтернатива — добавить корневой export `""` (второй путь резолва server) — не нужна: `./server` уже входит в список путей резолва server-entrypoint. Проверка реальным `plugin add` подтвердит.
3. **Миграция конфига — замена ключа, а не добавление.** Сначала бэкап (`opencode.json.bak-*`), затем удаление легаси-ключа `"plugin"` и только потом `opencode plugin add ocm991` — иначе хост отклонит установку как дубликат.
4. **Верификация до правок.** `plugin add` пробуется на текущем пакете (server-entrypoint уже есть): если срабатывает, правки сводятся к метаданным и документации; если нет — причина ищется в семантике хоста, не угадывается.
5. **Типы Promise API — официальный SDK как devDependency + `import type`** (решение согласовано с пользователем при планировании). Типы импортируются только как типы: у потребителя devDependencies не устанавливаются, type-only импорты стираются при исполнении — runtime-код SDK (effect, @opencode-семья) в дерево зависимостей плагина не попадает. Альтернатива (сохранить локальные структурные типы) рассмотрена и отвергнута: канонические типы дают tsc-проверку против реального API и снимают ручную синхронизацию при обновлениях хоста. Семантика `messageID?: string` (context-хук может вызываться без messageID) сохраняется независимо от источника типов. Граница типов: SDK подключён как data-поверхность (`Registration`, `SessionContext`, `Tool.Result` через `import type`), домены хоста (`Plugin.Context["session"|"tool"|"event"]`, полный вход context-хука, `ToolContext`, `Plugin.Plugin`) остаются структурными — SDK брендирует SessionID/AbsolutePath и требует полные наборы полей доменов, а тестовые двойники хоста конструктивны по структурным подмножествам поверхности (обоснование в src/plugin.ts:27-35); переработка доменов на полные SDK-типы — отдельная задача вне этого change.
6. **Версия — semver по сути правок; ориентир patch (0.1.1).** Правки метаданных и документации невидимы потребителю; миграция типов затрагивает только dev-окружение (SDK в devDependencies) и у потребителя тоже ничего не меняет. Minor — если в ходе применения всплывёт изменение, видимое установившим.

## Risks / Trade-offs

- [Холодный `plugin list` показывает «No plugins found»] → верификация всегда повторным вызовом из той же директории; в задачи это заложено явно.
- [`plugin add` отклоняется как дубликат при forgotten легаси-ключе] → порядок миграции: бэкап → удаление ключа → add; бэкап даёт откат.
- [Миграция типов потянет runtime-код SDK] → допустимая форма подключения зафиксирована в спеке (types-only); выбрано devDependency + `import type`; факт «SDK не types-only» проверен заранее; проверка сценария «установка не тянет runtime-пакеты».
- [Типы SDK могут расходиться с фактическим поведением v2.2.5] → при миграции сохранить семантику `messageID?: string` (фикс из смоука: хост может вызывать context-хук без messageID); поведение не меняется, тесты остаются зелёными.
- [Литерал в конфиге vs spec в реестре] → документация и конфиг используют голое имя `ocm991` (= `latest`), без пинирования версии.

## Migration Plan

1. Бэкап главного конфига (`opencode.json.bak-*`).
2. Удалить легаси-ключ `"plugin"` из главного конфига; выполнить `opencode plugin add ocm991`; убедиться, что пакет в `"plugins"`.
3. Внести правки метаданных/документации (по задачам); `bun run check` зелёный до и после каждой правки.
4. Верификация: повторный `plugin list` (плагин memory виден), `plugin check` — current, `plugin update ocm991` — обновлений нет; живой smoke в opencode-сессии: `memory_save` → `memory_list`, секреты редактируются, хранилище в `~/.local/share/opencode-memory` не пострадало.
5. Откат: восстановить конфиг из бэкапа; правки в репо — по git.

## Open Questions

- Публикация новой версии в npm — только по явному подтверждению пользователя по итогам верификации.
